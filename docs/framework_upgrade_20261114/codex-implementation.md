# Codex CLI 0.169.0 implementation and verification (2026-11-14)

Scope: independent Codex adapter and shared agent-tools, on core `133e93d` and OpenCode integration `6cdc877`. The current target is the official CLI `0.169.0`, not the separately bundled desktop CLI. No personal Codex configuration, trust settings, user business files, remote release, or shared model service was changed.

The existing `.codex-plugin/plugin.json` compatibility format remains. `SessionStart` matches startup, resume, clear, compact, and fork. The shell hook handles only a single plain unbounded `cat` with an in-workspace target; bounded reads, searches, shell compounds, missing session IDs, and bridge/state failures keep the native path. The pre-existing lock, atomic state update, 24-hour TTL and 512-entry cap remain. Hook timeout remains three seconds; timeout, invalid runtime and bridge/state failures now emit a short stderr fallback marker without copying child stderr or data, while native behavior remains available.

The standalone `scripts/check_codex_plugin.py` checks exact CLI version, generates the CLI's experimental app-server JSON schemas, validates request and response payloads, discovers the plugin and all six MCP tools, and invokes each against a temporary synthetic fixture. It tests Unicode character ranges, raw-reference isolation across actual app-server threads, same-size source replacement, and workspace confinement. It does not approve or inspect hook trust. Project trust, MCP availability and hook trust are distinct: in an isolated untrusted project the catalog exposed the plugin but it was disabled and MCP inventory was empty; after the isolated project was marked trusted, it was enabled and all six MCP tools were callable. Listing hook definitions does not establish their approval or execution.

Independent developer-command smoke is included in source archive allowlist and in the fixed 0.169.0 CI and release source-ZIP checks. Default installer doctor still checks local configuration and transport; it does not silently grant trust or run the deep host test. The standalone check intentionally uses a loopback non-model provider configuration and never sends a model turn.
