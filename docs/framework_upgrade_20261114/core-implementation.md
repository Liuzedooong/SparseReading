## Bounded collection candidate and source-version follow-up

The preceding one-file-only paragraph describes the earlier checkpoint; this candidate extends opt-in `source_manifest` to directories. The host must first authorize the directory, request a manifest without source-body reads, authorize each returned lexical and canonical path, and provide the one-use token on each operation. The manifest includes every regular file conservatively, rejects symlinks, traversal errors and directories with more than 1024 files, and binds directory and file metadata. A request-scoped ContextVar limits collection indexing, excerpt expansion, and raw selectors to the approved set; each content read checks membership and file metadata. Token-bound collection operations clear only the same conversation/artifact's old ready closure and guards, retaining output provenance; no cache-performance benefit is claimed. Files introduced after validation are not read through the collection reader. A replaced approved file is rejected before its content is read in the targeted tests. Native fallback remains necessary when any preflight/authorization/validation fails. The check and open remain separate: this is not an atomic sandbox against malicious concurrent filesystem mutation.

The method-binding audit found an additional A/B path collision involving trailing whitespace; the reproducer failed before the fix (`/tmp/sparseread-manifest-whitespace-before-20261114.log`). Canonical paths with boundary whitespace are rejected by this contract. `raw_ref` now includes source version metadata, old single-file references are rejected after same-size rewrite even when mtime is restored, and token-bound collection references additionally bind the frozen file-set metadata. References and their state are cleaned on session end. Text digest collection hashes before and after extraction and declines to cache if they differ; this does not prove a consistent snapshot against arbitrary concurrent changes.
